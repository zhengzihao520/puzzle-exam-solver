# 速度与准确度的实测边界

这份文件只记录**量出来的数字**和由它们得出的结论，不写预期。

## 1. 为什么步数下不来

落位本身 25 次不可省。其余步数都在“读切边”：每块举起一次、拍一张、放回，共 30 次（白块可跳过，故 25 次）。

于是**举起读**的下限是 25 + 25 = **50 步**，而考核的 `moveTarget = 33`。差的那一步不是调优问题，是方法问题。

## 2. 原地读形状：试过，不行

### 方法

不举起块，直接在托盘里看每条边外侧的窄条（宽约 19 px，横间隙 17.9 px）：

- 外侧窄条中部有亮块 → 凸起
- 窄条干净、但块身边缘中部内凹 → 凹陷
- 两者都没有 → 平边

判据取“中部 vs 两端”的差值（阈值 ±6 px）。

### 结果

同一局、同一批块，原地读数与举起读数逐边对照：

```
56 条边比较：26 条一致，30 条不一致（46%）
原地判定分布：凸起 14、平边 20、凹陷 22
```

**46%**，而要用它替代举起读，至少需要 ~90%（合成真值下 10% 读错仍能 6/6 完整装配）。

### 原因

邻块的凸起会伸进同一条窄条（间隙 17.9 px < 凸起 19 px），所以“这条边有凸起”既可能是自己凸起，也可能是邻块凸进我的凹槽。单帧下这两者在几何上就是同一个现象。这不是调参能解决的，是信息不足。

**结论：靠原地读把步数压到 33，此路不通。** 现实下限 ~50 步。

## 3. 那“准”卡在哪

装配求解已量过（`assemble.py --selftest`，合成真值）：

| 切边读数错率 | 完整解出 |
|---|---|
| 0% | 6/6 局，100% 块 |
| 10% | 6/6 局，100% 块 |
| 20% | 92% 块 |

所以求解器不是瓶颈，**读数才是**。而实拍的弱项非常明确：**平边漏读**。一局 25 块只读出 `平顶 3 / 平右 0 / 平底 4 / 平左 0`，而 5×5 棋盘每边必须有 5 条平边。

平边漏读的后果不是装配错，而是**边缘格缺候选**：边缘格只有拿到带平边的块才能放，读数说“没有平边”，那格就只能靠试。

## 4. 由此定的优先级

1. **平边读数**——一个良定义的图像问题（平边既无凸起也无凹陷），比原地读容易得多，且直接决定拒绝次数；
2. **拒绝率**——每次拒绝要付 2 步（放下 + 拖回原位）。实测 29 次尝试拒 6 次时是 35 步，拒 22 次时是 104 步；
3. 剩下的才是求解器调优（已经够用）。

## 5. 已经排除的错路（避免重复）

| 想法 | 实测结果 |
|---|---|
| 靠参考图做模板匹配 | 参考面板每格是同类**另一张照片**，原理上失效 |
| 靠画面连续性拼装 | 有利照片 19/20，平坦照片 6/20、7/20（`seam_test`） |
| 切边硬约束 weight=30 | 20% 读错时降到 83%，**比不用还差** |
| 原地读形状替代举起读 | 与举起读仅 46% 一致（本文第 2 节） |
| 从照片反推裁剪框来重测 | 25 块里 11 块与原读数不符；改为读数时把裁剪框写进 `logs/cuts.jsonl` |

## 6. 平边读数：阈值不是原因（把假设排掉了）

原本怀疑 `SHAPE_CUT = 0.35` 定得太低，导致平边被判成凸/凹。用合成真值量了分数分布：

| 真实类别（piececutter 约定） | tab 分数 | notch 分数 |
|---|---|---|
| 平边（58 条） | 恒 0.00 | 恒 0.00 |
| +1（视觉上是凹） | 0.00 | 中位 0.66 |
| −1（视觉上是凸） | 中位 0.71 | 0.00 |

平边分数是**精确的 0**，凸凹也分离得很开，所以阈值不是瓶颈，读数器在合成图上是准的
（`test_edges.py` 的 1200/1200 也印证这一点）。

结论：实拍失准来自**合成图里没有的东西**——引擎的 ~20 px 投影和 2 px 白描边，
它们会污染 `piece_mask`，进而污染轮廓剖面。下一步的实验应当是把这两样加进合成渲染，
复现后再定修法；在此之前不要再动阈值。
