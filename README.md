## 1. 站点规则（读源码确认，不是推测）

存档在 `recon/`（`main.js`、`puzzle_board.js`、`catalog.js`、`engine_PieceCutter.js`、`controls_new.js`）。

| 现象 | 源码依据 | 对算法的影响 |
|---|---|---|
| 参考面板每格是**同类别的另一张照片** | `catalog.js: alternatePhoto()`；注释写明 "a template match against the reference cannot solve the board - the class has to be recognised" | 像素匹配从原理上失效，必须做**类别识别** |
| **每块只对应唯一一格** | `puzzle_board.js: SOLUTIONS.set(piece, {x, y, row, col})` | 同类多块时，仅凭类别**无法**确定是哪一块（这是本项目的核心难点） |
| 块是**真锯齿块** | `PieceCutter.generateEdgeMatrix()`、`tabSize = 0.22*min(w,h) ≈ 18px`、`margin = 1.5*tabSize` | 角块两侧平边、边块一侧平边；形状是区分同类块**唯一**的可见线索 |
| 吸附条件 | `checkSnap()`：`dragging === piece` 且 `SOLUTIONS` 有该块 且 `dist < snapThreshold` 且 `hasAnchor()` | `snapThreshold = max(pieceWidth*0.14, 10*ratio) ≈ 15.7px`；落点必须**精确**；内圈块要求邻居已落位 |
| 吸附后不可再拖 | `pickPiece()` 里 `if (!p.isPlaced)` 才参与命中测试 | "抓住格子拖一下，格子还亮 = 这块已锁定"，可作为锁定判据 |
| 混淆块 | `main.js: decoySources`，`wantedDecoys = round(count*0.2)`；`SOLUTIONS` 无条目 | 混淆块**永远不会吸附**，不会算进通关 |
| 通关条件 | `isGenuinelyComplete()`：所有有解块 `isPlaced` 且 `DRAGGED === true` | 通关需要**每一块都被真实拖入** |
| **进度数字只在放对时 +1** | 站点 UI 行为（用户确认） | 这是唯一权威的成功判据（见第 5 节） |

|---|---|
| 棋盘 | `(463, 460, 530, 418)`，5×5，格 106 × 83.6 |

## 3. 视觉与分类

### 3.1 托盘取块

- 满托盘时用**缝隙网格**：真正的缝是贯穿整条带的窄黑条，按"这一列有 ≥75% 的像素是暗的"识别；
- 列检测必须**只在有块的行范围内**统计（托盘变空后上半部全黑，整条带统计会失效）；
- 托盘稀疏/块被挤在一起时退回**连通域**取块（一块面积 ≈ 112×85 = 9520px，明显更大的按块数拆分）。

### 3.2 类别识别

- 模型：`runs/cls/weights/best.pt`（YOLO11s-cls，15 类，598 训练 / 150 验证，val top1 **0.96**）
- 推理：**三视图集成**（imgsz 160/224 × 水平翻转），输出概率向量平均
- 实测（30 块人工标注的真实托盘块，作为真值）：

| 配置 | 准确率 |
|---|---|
| 固定网格 + 单次推理 | 26/30 |
| 实测格子矩形 + 三视图集成 | **29/30**（存 JPEG 后仍 29/30） |
| 只按类别匹配去拼（不做其它约束） | 实机只能命中"该类别在盘上唯一"的格子 |

### 3.3 白块判据（混淆块）

| 判据 | 结果 |
|---|---|
| 整格白像素占比 ≥ 0.65 | 判出 10 块（错，实际 5 块）|
| **中心一半区域白像素 ≥ 0.995** | **恰好 5 块** ✅（实测真白块 1.00，白底商品图 0.02–0.70）|

### 3.4 空格判据

| 判据 | 问题 |
|---|---|
| 均值 < 45 | 把夜景类暗块误判成空位（5 块）|
| 均值 < 45 且 `max` < 70 | 仍有残留亮点 |
| **均值 < 45 且 99 分位 < 20** | 空槽实测 8–13 / p99 8–9；任何照片 p99 都远高于 60 ✅ |

### 3.5 形状识别：用引擎自身的切块数学做模板拟合

站点引擎是开源的（上游 `playjigsaw/play-jigsaw-puzzles-online`，源码注释自称 "Part of
PlayJigsaw.net Open Source Engine"），`engine_PieceCutter.js` 已存档。块的四条边是贝塞尔曲线，
**轮廓只取决于四条边的类型（平/凸/凹），与照片内容无关**：

```
tabSize = min(pieceW, pieceH) * 0.22      # 106 x 83.6 -> 18.4px
margin  = tabSize * 1.5                   # 27.6px
canvas  = (pieceW + 2*margin) x (pieceH + 2*margin)   # 161 x 139
```

所以不必去"测量凸出多少像素"，而是把 **81 种边型组合（每边 平/凸/凹）逐一代入引擎的贝塞尔
控制点渲染成轮廓模板**，再与实际轮廓做 IoU 拟合，取最像的那一组。`piececutter.py` 是
`drawEdge` / `renderPieceToCanvas` 的 Python 移植。

实测（`piececutter.py` 自检）：

| 测试 | 结果 |
|---|---|
| 干净模板往返（生成 → 拟合 → 还原边型） | 12/12 |
| 缩放 1.0 / 模糊 1 / 无噪声 | 20/20 |
| 缩放 0.85 / 模糊 3 / 噪声 0.06 | 20/20 |
| **缩放 0.7 / 模糊 5 / 噪声 0.10** | **20/20** |
| 缩放 1.15 / 模糊 3 / 噪声 0.08 | 20/20 |

最佳与次佳 IoU 的差距稳定在 0.033，可作为置信度指标。仍未做的一步：真实屏幕上取得
"单块干净轮廓"（托盘块互相咬合，需要隔离），然后就能按边型唯一确定每块该去哪一格。

## 4. 执行层

主执行器 `place.py`。两条实测出来的数学事实：

- **指针 → 块的位移是 1:1**（`probe_map.py`：指针移 (+100,0) 块移 (+101,0)；移 (0,+100) 块移 (0,+100)）。
  所以只要**抓在块矩形中心**，块中心就会落在指针所指的点上。
- **吸附半径 = pieceWidth×0.14 = 15.7px**。抓槽位中心、瞄格矩形中心，实测残差 0–6px，
  是阈值的 1/3，一次到位。

每一步：

1. 抓槽位中心 → 移到格心 → 松手（1 步）
2. **锁定探测**：在格心按下、往 (+62,+38) 推一下、截图。
   已吸附的块被 `getPieceAt` 跳过（`if (!p.isPlaced)`），按下等于按在空处，画面不变 → 判定放对。
   **这个探测在"放对"时消耗 0 步**：没有 selectedPiece，引擎在 `onPointerUp` 里提前 return，不计数。
3. 推开后画面变了 → 块还在手上，**直接拖到该块的下一个候选格再松手**（每次重试 1 步，不是 2 步）。
4. 全部候选格都失败 → 拖回一个空槽位（1 步），**盘中不留块**。

顺序：外圈→内圈（`hasAnchor` 要求格子在边框上或邻格已放），同类别内候选格由少到多。

## 5. 判据（本项目最重要的一条）

**权威判据是引擎自己的行为：已吸附的块拖不动。** 这不是启发式——`getPieceAt()` 第一行就是
`if (!p.isPlaced)`，已放置的块根本不参与命中测试，按上去什么都不会发生。

"进度数字"这条路实测不可靠：**进度文字不在固定位置**。标定时的 y≈230–260 / x≈1200–1650
在另一次运行里是纯背景（最大亮度 69，没有任何文字），按区域裁图比较会静默失效——
它曾把我 3 次成功的落位全部判成 refused。

踩过的坑：

| 判据 | 结果 |
|---|---|
| 拖 1.1 格看格心是否让空 | 误判 |
| 亮度/变暗启发式 | 误判（悬停高亮 70–90 与暗块重叠）|
| 彩纸动画 | 误判 |
| 进度区平均差 | 裁取区随页面状态漂移 → 静默失效 |
| 小块微移后看原槽是否变空 | **误判**：移 24px 后槽位仍有 76% 被盖住，均值仍高 |
| **按下+推开，画面不变 = 已吸附** | **正确，且放对时 0 步代价** |

代价：`moveTarget = ceil(25×1.3) = 33` 是**评分目标，不是限制**（`recon/exame_mode.js` 注释写明）。
正确块 1 步、错误块 2 步（松手 + 拖回槽位），识别错得越多步数越贵：40 步铺了 11 格。

**单点探测会骗人**：按在空处也不会变，和"已吸附"长得一样。所以现在用**五点探测**
（格心 + 四个四分之一点，全部落在块矩形内）；五点连续落空，散块不可能做到。
第一版只有单点，报了 17/25，而游戏实际是 10/25——这个数差就是这样来的。

托盘栅格同样不能靠暗缝测：块走掉大半后暗缝消失，实测退化成 3 行、槽高 61px。
现在按引擎公式算解析栅格（`vision.lattice_slots`，步长 129.92 / 98.6，5 行 × 3 列），
与实况逐格核对一致（30 槽，左带 x=29/159/289，右带 x=1002/1132/1262，首行 y=435）。
靠坏栅格算出来的"空槽位"会把块停到槽与槽之间的缝里——这就是"棋盘右下角有留块"的来历。

## 6. 失败实验记录（数字）

| 实验 | 结果 | 结论 |
|---|---|---|
| 整图训练 15 类（598 张） | val top1 **0.96** | 整图分布 ≠ 运行时分布 |
| 合成块状裁片（15,900/2,800，imgsz 96） | val top1 **0.711** | 欠拟合，实机仍大量误判 |
| 30 张真实块高倍重复微调（`runs/cls_real`） | 自测 30/30，新局**塌缩到 desktop/tafei** | 过拟合，作废 |
| 固定网格切块（±12px 搜索） | 第 3 块得分 -9 | 那是**空位**，不是切歪 |
| 托盘列检测用整条带统计 | 读出 0 块 | 空行占比淹没有效信号 |
| 形状测量（阈值/轮廓中位数等 6 种取法） | 双平边 3–4 / 单平边 11–12 / 无平边 9–10，应得 4/12/9 | 阈值法不可靠 |
| **形状测量（引擎模板 IoU 拟合）** | 合成 20/20（含缩放 0.7、模糊 5、噪声 0.1） | **方法成立**，只差真实轮廓的干净获取 |
| 进度区 `(1540,225,250,60)` 平均差 | 假的 25/25（实际 0/25） | 裁取区不含数字 |

## 8. 怎么运行

**前置条件**：浏览器窗口**最大化**且在前台，页面停在考核里、棋盘可见。
程序会先自检窗口与前景，不满足就直接退出，不会乱点。

**最省事**：双击仓库里的 `dry.bat`（只看）或 `run.bat`（执行）——它们会等你 10 秒去点浏览器，
结束时把退出码打出来。

```powershell
cd F:\exam_next
D:\python\python.exe stateless.py --dry           # 只识别 + 规划，一个鼠标动作都不做
D:\python\python.exe stateless.py --go            # 执行（对着参考面板匹配，25 次落位）
D:\python\python.exe stateless.py --go --edges    # 额外读切边（每块多 1 步，诊断用）
```

`--dry` 会打印：识别的格数、找到的块、参考面板匹配覆盖了几格、每格分到哪块。
**看清这几个数再加 `--go`。**

**常见报错**：

```
foreground: 199x34 on 1920x1080 [某窗口标题] -- abort: exam page is not the foreground window
```

方括号里就是它当时看到的那个窗口——前台不是浏览器。从终端按回车启动时，前台往往还是终端自己。
加 `--wait` 留出切换时间，看到提示后再点一下浏览器：

```powershell
D:\python\python.exe stateless.py --go --wait 5
```

另有两条硬条件：窗口标题里要有 `Edge` 或 `Chrome`；窗口要**最大化**（宽 ≥ 97%、高 ≥ 93% 屏幕）。
任何一条不满足都会以退出码 2 结束，**一个鼠标动作都不会做**。

**离线自检（不动鼠标、不用开页面）**：

```powershell
D:\python\python.exe assemble.py --selftest 6            # 装配器：已知答案的合成局
D:\python\python.exe assemble.py --selftest 6 --err 0.1  # 切边读数错 10% 时
D:\python\python.exe test_edges.py --trials 300          # 切边读数（含引擎投影）
```

**模型**：`runs/cls/weights/best.pt`（YOLO11s-cls，15 类，11 MB）已随仓库提供，不用重训。
确需重训：`tools\fetch_catalog.py` → `tools\build_dataset.py` → `tools\train_yolo.py`。

环境：Windows 10、Python 3.14、torch 2.15.0+cpu、ultralytics 8.4.213、opencv 5.0.0、pyautogui
（必须先 `_enable_dpi_awareness()`，否则窗口尺寸会被读成 1536×864）。

**只打 5×5**：程序不再区分 3×3 / 4×4，也不需要 `--size`。开局先数托盘——5×5 恒发 **30 块**
（25 格 + 5 块混淆），数出来的块数不在 28–32 之间就打印
`abort: ... not the 5x5 deal` 并以**退出码 3** 结束，**一个鼠标动作都不做**。

（早期版本按“块宽反推格数”，而每块都带约 20px 投影、块宽被撑到 133px，`560/133 = 4.2`，
于是把 5×5 认成 4×4。现在格数是常量，块数只用来判断“这是不是 5×5”这一件事。）

## 9. 当前状态（全部为实测数字）

### 最优路径：对着参考面板做图像匹配

**一局 5×5：25 步、25/25、0 拒绝、0 次读切边**（页面记 用时 05:40 / 总步数 25 / 已拼格数 25/25）。
这是理论下限——每格 1 步，且低于考核的 `moveTarget = 33`。

原理：面板格与托盘里那块是**同一张照片**（实测自家格相关 0.662 vs 最强错误格 0.380，
21 格里胜出 20 次；改进后 0.67/0.91）。于是每块的归属可以直接“看参考图”读出来：
零步、不需要读切边、不需要类别猜测，也就不存在拒绝。实现见 `panel_match.py`。

三项参数把匹配器从 0.60/0.85 提到 **0.67/0.91**：用**彩色**（同类的差别在色相不在亮度）、
匹配分辨率 **96×72**、对齐搜索交给 `cv2.matchTemplate`（一次覆盖 ±9px）。

### 已知限制（有数字，不是猜测）

1. **33 步做不到**：落位 25 步不可省，其余 25 步是“举起读切边”。“原地读”实测与举起读仅
   **46% 一致**（间隙 17.9px < 凸起 19px，邻块凸起伸进测量窄条，单帧无法区分）。现实下限 ~50 步。
2. **平边计数仍偏**：一局 30 块里，只用颜色读数得 7/10/6/6（合计 29，多读），现在并集得
   6/0/6/3（合计 15，右平边全丢），真值是 5/5/5/5（合计 20）。两个读数器往相反方向偏，
   换规则治不好；下一步是按“每边恰好 5 条”做排名裁定。详见 `docs/limits.md` 第 7 节。
3. **白块之间没有可读身份**：5 个白块的参考格是纯白瓦片（均值 255，无图案），空棋盘格也不渲染形状
   （空格与格间缝隙同为灰度 23.0）。实测了三条路都不成：读空格的“孔”轮廓（没有孔）、读已放置块的
   四边反推（22 个相邻对里只有 3 对能互相印证）、白块图案匹配（白格没图案）。所以白块只能由引擎拒绝
   来仲裁，代价是每次 2 步。白块的四边**可以**从它自己的轮廓读出来（亮块在暗托盘上，自校准法在
   5 块里 4 块可读），目前只用来排序候选，不用于唯一判定。
4. **拒绝仍是主要成本**：每次拒绝 = 2 步（放下 + 拖回原位）。实测 29 次尝试拒 6 次是 35 步，
   拒 22 次是 104 步。

### Part 3（照片 + 纯白混合，考核要求的模式）

拼完了，而且是**录下来的**：页面自己弹出结算「拼图完成！」——**已拼格数 25/25，用时 07:01，总步数 85**
（`demo/part3_perfect_25of25.mp4`，日志 `logs/perfect_run.log`）。要点：

1. **换局必须忘掉旧的“拒绝对”**：`logs/tried.json` 里的 (块, 格) 是槽位序号，不是身份，换一局所代表的
   完全是别的块——以前每局开局就带着上一局 40+ 条拒绝记录，好候选被直接跳过。
2. **候选数按轮次放开**：每格每轮从 2 个候选升到 `min(4, 2+轮次)`，收官阶段（剩余 ≤3 格）放开“每对最多
   拒 3 次”的上限——锁定探测本身有 1–3 格的漏判，把“拒过 3 次”当成定论会直接判死一个格。
3. **收官时把整盘剩余块都放进候选**：最后几格里真正能放的那块，有时被识别器判成了别的类别；只要
   “同类别候选”非空，原来的兜底分支就不会执行，于是它永远轮不到。实测这一条是 24/25 与 25/25 的分界。
4. **白块排在最后、且只给白格**：5 个白块互相无法区分，每次猜错要花 2 步（一局里 22 次拒绝 = 44 步，
   全是白块之间）；而引擎只看几何，白块放到照片格上会锁住，把白格饿死。

步数上要说清楚：**总步数 85 对目标 33 是超的**。25 次落位不可省，多出来的 60 步几乎全是拒绝后的
“放下 + 拖回原位”，每次 2 步；白块的仲裁占了其中一半以上。

同一份代码另有三次 24/25（`demo/part3_run_24of25_*.mp4` 里能看到），差的那一格有两种原因，都查过：

- **分类读错**：如“椅子格 3 个、椅子块 1 个”，真块被判成别的类，日志自己会报 `SHORT ... some piece
  is read wrong`。
- **块被同形的别格“偷走”**：引擎只按几何吸附，两格若卡口相同、块就能锁进不属于它的那一格；锁上就
  再也拖不动，等轮到真格时那块已经用掉了（一局末尾剩下唯一的椅子块，在“椅子格”上连拒 3 次就是这种）

### 白块“按凹凸一步定位”：做到哪一步，以及为什么只保留一半

能不能靠凹凸一步定位？分三件事，都量过：

1. **白块自己的凹凸**：能读，0 步。白块是暗托盘上的亮块，轮廓就是卡口形状；自校准剖面法
   （`white_edges.py`）在 5 块上给出 3–4 个可读面，签名互不相同。也已修掉“托盘槽距 18px < pad 26px
   导致把邻块边缘算进来”的问题（改为只保留中心连通域）。
2. **白格需要什么凹凸**：页面不渲染。空棋盘格灰度恒 23.0（与格间缝隙相同），没有形状可读。
3. **从邻居反推需求**：能做，但只到 83%。空格是暗的、邻居是亮照片，交界轮廓可测（给每条边一个带符号的
   “侵入量”）；用“最终锁进该格的那块”当裁判核对：**已知面 10/12 一致**。作为**过滤器**用会把真块排除
   （实测拒绝 21 次 vs 之前 9 次），作为**排序**用也没改善（15 次白块间无效尝试）。所以只保留第 1 条里
   最可靠的**平边**，交给 `shape_fit` 排序——白块之间的无效尝试从 9 次降到 **6–7 次**，两局结果
   25/25、23/25。

结论：**“一步定位”目前做不到**，因为白格的需求面有一半是猜的（邻居没填就没有信息），而读数每次有
~1/6 的错。要真正做到，得让引擎把空格的形状画出来，或让白块之间在视觉上有别的差别。

### 一次真实回归：白块读数不能进 `edges`

把白块的四边读数接到 `edges` 之后，**照片模式也跟着退化了**：`edges` 同时喂给 `jigsaw` 规则求解器，
而照片模式的托盘里可能有“白底照片”被分类器叫成 `blank`；这些白块的签名一旦进了求解器，规则解就在
25 格上“完整”了（`rule solver: 25 cells`），于是**覆盖掉按参考图得到的计划**，一局能拖到一百多步。

修法（`8398c38`）：白块读数存进独立的 `white_sig`，只在**这一局真的有白格**时才算，`edges` 保持原样。
验证：同样的照片模式连跑两局 —— **24/25（40 步、8 次拒绝）**、**25/25（31 步、3 次拒绝）**，日志里
`white pieces` 一整块都不再出现。


### 提速与准确率的调优记录（Part 3，全部实测）

| 版本 | 做了什么 | 3 局结果 | 平均步数 | 平均拒绝 |
|---|---|---|---|---|
| 调优前 | 只按参考图 + 类别兜底 | 25/25、23/25、21/25 | 71 | 23 |
| 现在 | 加“只许拖去自己最像的格” + “跨类别兜底只在收官” + 白块平边排序 | 24/25、23/25、23/25 | **52** | **14** |

变化点与理由：

1. **只许拖去自己最像的格**（`owns`）：引擎只按几何吸附，一块若被拖进“同形但不属于它”的格，就会锁死
   在那里、再也拿不出来，它自己那格从此无解——这是 24/25 最常见的丢格方式。现在托盘还满时只允许
   “这块最像这格”或“计划就是这块”；自己那格已被占用的块不受限制（否则会被全程封死）。
2. **跨类别兜底只在收官阶段**：实测 23 次拒绝里有 **17 次**是跨类别（elephant→chair、suitcase→tafei），
   在托盘还有正确类别时几乎必错；把它们推到剩余 ≤3 格时才做，跨类别拒绝从 17 降到 **3**。
3. **白块只贡献“平边”**：见上一节，卡口推算只到 83%，只保留最可靠的平边用于 `shape_fit` 排序。

被回退的尝试：**“白格只接受白块”**——实测反而更差（20/21/22 格、平均 64 步、21 次拒绝），已 revert。
`--loose` 可退回“不限格”的老行为（步数更多、被误读的格救得更早）。

结论：**速度提升约 27%（71→52 步）、拒绝减少约 40%（23→14）**，完成率在 3 局样本内没有可测差异
（都在 23–25 格）。剩下那 1–2 格的根因没变：白块之间无法区分、以及分类把某块读成别的类。
### 上一版 README 里被推翻的说法

- “同类内顺序猜错要花 32 步”→ 根因是**锁定判定**用了绝对亮度阈值（暗块只掉 13 < 25），
  把被拒绝的落位记成已放好，之后又把刚放对的块拖走；现改为相对降幅 + 纹理降幅。
- “白块 5/5 对上 5 个白格”→ 那是按亮度均值判的，实测**分不开**（白块 239 vs 白底照片 236）；
  现按中心半区白度**排名**取前 k 块。
- “失败块回托盘”→ 原先是“回第一个空槽”，会让块漂出栅格、指纹再也找不到；现在**回原抓取点**。

## 10. 注意事项

- 站点网络不稳，`curl` 偶发 `code=000`，下载需 `--retry`；`Invoke-WebRequest` 会超时，用 `curl.exe`
- 浏览器窗口必须**最大化**且**在前台**，否则坐标与截图全部失真（程序会自动检查并拒绝运行）
- 鼠标按键保护：所有拖拽都包在 `try/finally` 里，异常也会 `mouseUp`；进程退出时再释放一次
- `pyautogui.FAILSAFE` **已关闭**：它会在指针停在屏幕角落时于拖动中途抛异常，而那时按键已经按下，
  下一次抓取就会把棋盘拖乱。我们自己的移动都由 `_safe()` 限制在边界内 40px，那个保护只可能被外部原因触发
- **棋盘一完成就停止一切鼠标输入**：完成后页面会切到结算界面，此时往格子坐标按压/拖动，
  等于点击界面上的按钮（实测把页面点成了新局）
